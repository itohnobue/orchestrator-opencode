QUALITY RULES (CODE):
- Read every file BEFORE modifying it
- Every change MUST be minimal — only what task requires
- Follow existing code patterns and conventions
- Before adding code: Grep for existing similar functionality
- Do NOT expand scope beyond task
- Partial honest results > false completion — report actual completion %
- Cannot determine → "UNABLE TO DETERMINE", do NOT guess
- After completing a logical batch of edits (not after every single edit): run lint command
- Before calling a function/method: Read the source file to verify it exists with that exact signature
- Root cause first: investigate root cause before proposing workarounds (timeouts, retries, skip logic)
- Do NOT add error handling (try/catch, null checks, validation) for states the code cannot actually reach. Handle only reachable error paths — guarding impossible states is a common LLM-codegen anti-pattern that clutters code and masks real logic
- If the task carries a RESEARCH DATA section (routed research digest — the full report path rides under the header, consult it on demand), use it as your briefing — do not redo the research. Your task's PRIOR CONTEXT and MUST ANSWER take precedence over the research emphasis. Research "known-good"/trap statements are PROVISIONAL: if the module contradicts them with evidence, the finding stands with the evidence. Do not suppress a real defect because a research statement calls it "by design" or "not a bug"

Mandatory verification (skip = report auto-rejected by lead):
- After ALL code changes are complete: run the fastest meaningful PARALLEL-SAFE verification of your change — compile/syntax check of your changed files, the test files covering your changes, or an isolated probe. NEVER run the full test suite or a full project build: other agents are editing and running concurrently (not parallel-safe — shared build dirs, ports, databases, fixtures); the full suite runs only in the build-gate/TEST stage (the build-gate agent is the exception — it runs it solo by design)
- Paste the ACTUAL command and its output (pass/fail counts, specific failures) into your report
- Do NOT write "all checks pass" without pasting the real output
- If verification fails on YOUR OWN change: fix it and re-run BEFORE reporting (abort conditions apply after 3 attempts)
- A stale test asserting pre-fix behavior: update it if it is within your WRITABLE FILES, otherwise report it as a TEST-UPDATE finding — do NOT silently delete or weaken pinning tests
- Suspected issues you examined and dismissed during your change MUST be recorded in the report's "Investigated-and-Rejected" section with the dismissal reasoning + file:line — HIGH/CRITICAL-claim dismissals are re-examined by verification, so document all of them honestly. If nothing was dismissed, write "NONE"
- If no parallel-safe check exists for your change: run a compile/syntax check, state the gap, and note that the build-gate covers full verification

Anti-shortcut thoughts (slow down if any of these appear in your reasoning):
- "This is probably fine without testing" → run the parallel-safe verification command, paste the actual output
- "The error looks flaky, I'll retry and move on" → investigate the cause; flakiness hides real bugs
- "I'll suppress the warning/error to get it passing" → suppression is not a fix; find the root cause first
- "I'll skim the file instead of reading it before modifying" → read it fully; skimming IS the failure mode
- "The previous code does it this way so it must be correct" → existing patterns can be wrong; verify behavior against requirements
- "This is taking too long, I'll stop here" → no time pressure exists; report partial honest results, don't fake completion
- "I'll run the full suite to be sure" → NEVER. It is not parallel-safe with other agents running; the build-gate/TEST stage runs it. Use a parallel-safe check instead
- "I'll stash changes to get a clean build" → NEVER stash. Other agents' changes in the working tree are NOT yours to clean up. Report "NOT VERIFIED: pre-existing errors in [other files]" and continue
